## 修复前发现（历史证据）

优先级约定：P1 应在候选发布前修复；P2 是已确认的功能缺口，应在对应功能交付时关闭。
以下描述的是修复前行为，不再代表当前版本；当前状态见上表。

### R1 · P1 · 站位保存用最新版本替旧草稿授权，可能覆盖外部修改

位置：[app.js](../skills/short-drama/assets/dashboard/app.js)，
[服务端版本比较](../skills/short-drama/scripts/dashboard_server.py)。

触发过程：在站位视图开始调整后，另一编辑器修改同一场次的人物坐标或群演信息；
此时点击“保存站位”。`saveStaging` 先 GET 当前文件，再把刚取得的 `file.version`
作为 POST 的 `expectedVersion`，而提交的位置仍来自原来的 `draft`。
服务端比较的是最新版本与最新版本，因此不能识别这份草稿是在外部修改之前形成的。
同名人物与物件仍存在时，旧草稿会覆盖对方的站位更改。

已执行实际 `saveStaging` 函数的 Node VM 最小复现，用内存 API 替身隔离网络与磁盘。
模拟打开版本为 `aaaa…`、外部修改后的版本为 `bbbb…`，实际发送 `bbbb…`，位置仍为旧草稿的 `0.4`。

修复方向：让 episode/staging 响应携带对应 Markdown 的版本，在草稿创建时固定它；
保存时发送这个原版本。外部修改后应收到 409，并保留可复制或重新合并的本地草稿。
现有服务端冲突测试直接提交旧哈希，未覆盖前端在保存时换成新哈希的行为。

### R2 · P1 · 节拍覆盖既不约束来源场次，也把少量相同文字当成承载证明

位置：[匹配函数](../skills/short-drama/scripts/creator_markdown_check.py)，
[调用点](../skills/short-drama/scripts/creator_markdown_check.py)。

`ScreenplayBeat` 带有 `scene`，但 `_matched_shots` 不读取它；所有场次的镜头一起匹配。
长段落只需四个连续相同字符，短段落门槛还会降低；来源短引文只需是原文的子串也可通过。
已有 `shot_scene_map` 并未传入这条覆盖链。

两项内存复现：

- `EP001-SC001` 的“许棠把铜钥匙丢进雨水井。”仅出现在来源为 `EP001-SC002` 的镜头中，
  `_check_beat_coverage` 仍返回空错误列表。
- 剧本写“许棠把文件撕成碎片扔进垃圾桶。”，同场镜头写“许棠把文件仔细叠好放进保险柜。”，
  `_matched_shots` 仍返回该镜头。两个动作的结果相反，公共开头已经足以通过。

另用完整 creator-first 文档集复现：在 SC001 新增“江晨将第七张红色便签埋入柜底。”，
完整校验先报一个漏拍错误；只把这句引文加到 SC002 已有人物依据的镜头来源后，
同一完整校验返回零错误。原有逐场引用检查没有兜住这次跨场误认。

修复方向：先用已解析的来源场次限制候选，再以可核对的来源引文建立承载关系。
弱文字相似度只能作为待核对提示，不能宣称已证明动作、对白或生产标签被承载。
修订必须保留“脚本核对确定性事实，创作判断归创作者”的边界。

### R3 · P1 · 参考图过期状态没有沿父图依赖传播，来源缺失也会被放过

位置：[来源检查](../skills/short-drama/scripts/dashboard_server.py)，
[父图比较](../skills/short-drama/scripts/dashboard_server.py)。

Dashboard 会读取每张输出的当前字节；但处理派生关系时，只比较父图 manifest 内的
`sha256` 与子图记录的 `depends_on_output.sha256`，没有比较父图当前文件的字节或父图已经计算出的状态。
父图片被修改、删除或不可读而账本未改时，父图会过期，派生图仍可显示“当前”。
此外，来源文档只有在 `source_text is not None` 时才比较；来源被删除或无法读取时，
这条检查被跳过，输出仍可显示“当前”。

使用临时合成项目与现有参考图夹具执行的结果：

| 输入状态 | 正面锚点 | 派生正脸 |
|---|---|---|
| 初始状态 | current | current |
| 只修改锚点图片字节 | expired：输出图片字节已变化 | current，无原因 |
| 恢复图片，再删除来源文档 | current，无原因 | current，无原因 |

这是 Dashboard 的可信状态问题。生产工具的
[`_verify_reference_dependency`](../skills/short-drama-produce/scripts/production_tool.py)
会重新核对父输出字节，本次没有发现同样的付费执行绕过；不能把界面缺陷扩大为生产闸门失效。

修复方向：先解析全组的来源、输出与依赖，再递归求状态；来源缺失应显式记为不可验证或过期。
依赖验证要处理父文件缺失、父字节变化、替代版本、跨层依赖和循环，不能依赖 view 的排序。
现有 `test_source_change_png_tamper_and_parent_update_are_expired` 的注释声称验证派生状态，
但只断言了锚点，而且没有真正恢复上一步修改的来源，因此未覆盖此缺陷。

### R4 · P2 · 站位草稿没有接入离开和关闭页面的未保存保护

位置：[切换项目](../skills/short-drama/assets/dashboard/app.js)，
[关闭页面](../skills/short-drama/assets/dashboard/app.js)，
[清空草稿](../skills/short-drama/assets/dashboard/app.js)。

站位修改保存在 `S.stagingDrafts`，而离开提示只检查 `S.edit?.dirty`，即原文编辑器。
调整站位后直接关闭页面、刷新或切换项目，不会触发对应的未保存保护；切换项目还会重建
`stagingDrafts`，丢掉这批修改。站位面板显示“有未保存的站位调整”，却没有覆盖相应离开路径。

此项由事件注册、项目切换与状态清理调用链确认，本轮未启动浏览器复演。
普通的同项目视图切换仍可能保留内存草稿，不应误报为所有导航都会清空。

修复方向：统一检查原文与站位的未保存状态；关闭、刷新和切换项目使用同一保护入口，
并允许在拒绝离开后继续保存原草稿。

### R5 · P2 · 跨镜对白的估时又被全部归到第一个匹配镜头

位置：[记录首个匹配](../skills/short-drama/scripts/creator_markdown_check.py)，
[逐镜合计](../skills/short-drama/scripts/creator_markdown_check.py)。

逐句检查会累加所有匹配镜头的时长，但之后把整句加入 `first_matches[matches[0]]`，
再次用第一镜的时长检查整句。这样，同一句对白合法跨切两个镜头，仍可能被误报为说不完。

内存复现：项目语速为每秒 3 字，“今天下午我们一起回去取那个重要文件。”约需 5.7 秒；
两个承载镜头各 4 秒，总计 8 秒。检查仍报第一镜“合计约需 5.7 秒，超过镜头 4 秒”。

修复方向：只对有明确承载边界的对白进行逐镜预算；跨镜台词按明确连续区间或已声明分配核算。
没有分配证据时报告估算与待核对项，不能任意把全部发声成本压到第一个相似镜头。

### R6 · P2 · 新诊断只有 CLI 完整消费，Dashboard 没有接入

位置：[episode 派生](../skills/short-drama/scripts/creator_views.py)，
[分组局部校验](../skills/short-drama/scripts/creator_views.py)，
[服务端组装](../skills/short-drama/scripts/dashboard_server.py)。

`diagnose_episode` 能输出 `errors` 与 `diagnostics`。Dashboard 的 `read_episode` 则主要收集
解析异常和复制分组问题，没有统一收集跨文档校验与资产诊断。
`usable_groups` 即使调用 `validate_documents`，也只筛选与分组/成员相关的错误，且传入
`project_root=None`，因此不会消费项目已接受的语速；它也没有传入 diagnostics 容器。

内存复现：给 creator-first 样例增加一段没有镜头承载的“纸条塞进抽屉”动作，
checker 明确报出第 77 行遗漏；同一组文档的 `read_episode` 返回 `problems=[]`，也没有 diagnostics 字段。
因此不能声称这批质量检查已经在创作台中闭环。

修复方向：在安全读取的同一份文件快照上，构建统一的结构错误与非阻断诊断结果；
前端分别显示可执行的修订提示与信息提示。不要为接入诊断绕开现有目录固定、路径约束或符号链接拒绝。
文档数量推导出的“提示词就绪”与检查通过应保持清晰区别。

## 仓库组织与开发质量

当前目录分工合理：`skills/` 是独立安装单元，`tools/` 是仓库开发/迁移工具，
`tests/legacy/` 是旧行为回归支持，`examples/` 是合成输入，`evaluations/` 是证据与评估，
`.agents/notes/` 记录决策，`.clawhub/` 与 `.release/` 处理分发。没有依据把两个仓库直接混成一个目录树，
或把开发工具塞进各技能运行包。

主要维护成本集中在几个大文件：`creator_markdown_check.py` 同时负责引用、声音、节拍、空间几何与交付组；
`dashboard_server.py` 同时负责安全文件访问、参考图状态、场景回写和 HTTP；`app.js` 同时负责所有页面、
编辑器和状态。文件大本身不构成缺陷，但这次三个重要问题都发生在这些职责的交接处。

建议在各自技能目录内拆分解析、诊断、参考图状态与保存服务，保持原入口兼容；
不要为了去重增加跨技能运行时导入。自包含约束造成的解析重复应由共同的行为夹具对照，
而不是依赖文案字符串断言。优先补上述实际遗漏的边界行为，再考虑文件拆分。

分发核对已完成：

- `.clawhub/publish.json` 的变更包与受精确依赖影响的伴随包已更新版本、重算摘要；
  使用工作流固定的中央控制脚本与 ClawHub 0.23.3 SDK，离线核对全部 11 个包的文件路径、大小、SHA-256 与包摘要。
  比较本轮整理前的 manifest，未出现内容改变却未更新版本的条目。未调用远程发布、安装或 registry 写入。
- `docs/third-party/shuohao-adaptations.json` 明确来源文件与目标实现范围；三个受影响技能各自携带
  `THIRD_PARTY_NOTICES.md`、Apache-2.0 正文和上游 NOTICE。真实中央打包结果已验证这些文件进入各自独立包。

## 采用的修复顺序与关闭标准

1. **先保护创作修改：R1、R4。** 页面打开后外部修改应产生冲突；旧草稿可恢复；
   切换项目、刷新和关闭页面均不能静默丢失站位修改。
2. **再保证参考图状态可信：R3。** 父图字节修改/删除、来源缺失与多层派生都会传递相应状态，
   生产依赖核对保持原有强度。
3. **修正检查器证据：R2、R5。** 跨场相同文字不能代替本场承载，反向动作不能靠公共前缀过门，
   有明确跨镜分配的对白按实际区间估时。
4. **把相同结果交给 UI：R6。** 同一文件快照下，CLI 与 Dashboard 对阻断问题和信息诊断一致，
   项目语速能够进入显示结果。
5. **最后做分发闭包核对。** 根据实际目标包处理来源说明、版本锁和固定快照；
   当前没有 Git 元数据，不在本轮虚构 commit、PR 或正式发布结果。
